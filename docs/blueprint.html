What Munshi is

A complete suite for small shops of three kinds: a kirana, a clothing shop and a salon. It keeps the books, runs the counter, hosts each shop's website, takes bookings and orders, and runs an AI back office that notices problems and drafts fixes. A named person approves every change to the books.

The One Guarantee

One promise outranks every feature. Every design choice on this page exists to keep it, and every review checks both halves.

Nothing changes the books without a named person's approval, and every number shown traces to a ledger row.

Clause 1

Nothing changes the books without a named person's approval

The rule for what counts as a book, applied to every table: a row is a book if it changes what is owed, held, sold, priced, paid, stocked or promised to a person, or records a staff member's work or pay, or is a message Munshi sends to a real person.

Everything a member of the public submits, every calendar hold, every piece of evidence and every setting is ops. A book row is written only by a person's own command or an approved draft. An ops row is written by the role whose job it is, and a trigger decides which columns may change and how.

Clause 2

Every number shown traces to a ledger row

A number on any screen, site or API response is a cell of a snapshot that core minted from a named read of the books. Its address is written

⟨snap:ID·row·col⟩

Every snapshot also answers ⟨snap:ID·0·_count⟩, its row count, so an empty result can be cited ("no overdue credit"). A ref that does not resolve renders "Cannot verify", never a number.

The two readings you confirmed (D-045)

WhatsApp cart totals are derived figures

A cart is built by an anonymous customer, so nothing is minted for it. Each line price is a published cell. Code, never a model, computes the line totals and the total with the counter's own line function: quantity in milli-units × unit price, rounded half away from zero to the paisa, added in whole paise. The response carries the refs it used and says "at today's prices · the shop confirms". An offer code travels as text only; a cart never shows a discount.

Gate CART1 takes every stored cart, reads its release's cells for its lines, recomputes every figure with the same function, and must match what the API returned. At the counter the sale re-derives the real price; a cart total is never read back as a price.

Slot times are roster times

Free slots are computed live from the calendar: who works at that shop that day, minus leave, holidays, closed hours and every held, requested or confirmed booking, on a 15-minute grid where the whole service fits. Each slot names the roster row it came from (shiftRel, shiftId); the hold stores it, and the database checks the booking against that row. No amount is shown with a slot.

Gate SLOT1 recomputes every offered slot and every booking from its stored roster row and the bookings, and must match. A booking that names a roster row not in effect that day is refused.

The audit chain, and verify_books

  • One gapless hash chain per shop: hash(n) = sha256(hash(n-1) ‖ canonical(entry n)), written by the trigger under a per-shop lock. Each entry names the acting member. Every book row has exactly one entry.
  • A book row's entry stores the sha256 digest of the row, not the row (913 bytes an entry against a row of about 300, measured in review). The hashing functions pin UTC so a digest written in one time zone verifies in another; gate VB1 writes under UTC and verifies under Asia/Kolkata.
  • audit.verify_books(shop) walks every books table and reports each row whose digest no longer matches (digest_mismatch), each row with no entry (no_entry) and each entry whose row is gone (no_row). An owner who disables the triggers and edits a sale is caught.
  • The jobs runner verifies from the last checkpoint nightly and writes a new one. The latest checkpoint's head is shown in Settings → Books integrity so an owner can note it down, and is written to the structured log daily.
  • Stated residual: the chain is unkeyed. The owner role can rewrite rows and re-hash the chain and checkpoints; only the head kept outside the database catches that. Log retention on Hobby is UNVERIFIED.

  • Reuse: a member's display read reuses the newest snapshot with the same read, params and rows hash, made less than a day ago, so a reused snapshot is at least six days from any purge. Agent runs, watchers, evidence and releases always insert.
  • Pins: triggers on the citing rows write a pin in their own transaction: drafts, findings, answers, briefs, site releases and spreadsheet batches. A pin is never deleted.

Loyalty points

A named customer earns floor(net × earn_per_100 / 10000) points per sale. Redeeming at least the minimum writes a redemption and a loyalty discount, never more than the net after offers. The balance is the database's, under a per-customer lock; a client's points are never read.

Packages: prepaid packs and memberships

The owner creates a plan (its item, price and lines in one transaction). A sale of a package line needs a customer and creates the holding. Any role redeems a session at either branch. Expiry is a draft the owner approves, and goes stale if a redemption lands first. In the journal a sale credits package_liability; a redemption moves that session's share (remaining value ÷ remaining sessions, in whole paise, the last session takes the remainder) to sales; an expiry moves what is left to package_breakage. Balances are set by the database under a per-holding lock and never go below zero.
