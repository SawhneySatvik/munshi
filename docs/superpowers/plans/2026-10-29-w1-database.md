# W0 + W1 · Database rebuild: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild Munshi's database from ordered schema files (`db/schema/00–90`). It includes the schema review's (R4)
fixes, the capability switches and orders. Every gate and red-proof runs on it. Today's suites stay green on the old
path until W2 retargets them.

**Architecture:**
- **The dual build.**
  - `db/migrations` with `db/test/global-setup.ts` (v1, PostgreSQL 18 embedded) keeps serving today's suites.
  - `db/schema` with `db/test/v2/global-setup.ts` (v2, PostgreSQL 17 embedded, through an npm alias) serves every new
    gate.
  - `db`'s test script runs both.
  - The local dev database for v2 lives in `.run/pg17`, so `pnpm dev` (v1, `.run/pg`) keeps working.
- One Opus migrator writes the schema files serially. Harness, spreads and doc lanes run beside it in disjoint
  territories.

**Tech Stack:** PostgreSQL 17 (`embedded-postgres-17` → `npm:embedded-postgres@17.10.0-beta.17`, FACT: published),
node-postgres 8.23.1, vitest, TypeScript run by Node 22 directly (`node file.ts`, as today).

**The DDL-level spec is `docs/BLUEPRINT.md` §2–§3 (after W0) and `docs/superpowers/specs/2026-10-29-munshi-platform-design.md`.**
- Each table, key, grant and trigger rule is stated there; this plan does not copy that DDL a second time.
- The tasks below give the order, the files, the interfaces, every gate with its red-proof, the commands and the
  commit points.

## Orchestrator's rulings on R4 (binding on W0 and the migrator)

`R4` = `hackathon/meta-ai-developer-hackathon/review-2026-10-29/R4-schema-review.md`.

1. **Fold every rank-1 and rank-2 finding** (B1, M1, S1, C1, O1, and N1–N7, K1–K6, I1–I8, W1, G1, G2, R1) at the
   BLUEPRINT line it names. Fold the rank-3 table too, with these exceptions:
   - K10: overnight hours stay a stated limit.
   - W5: the ref keys are accepted at this scale.
   - N12: give `ops.tenant` an owner-only `U(name, count_max_age)` through a `tenant_guard`, audited. No new table.
2. **Capabilities: the approved spec §2 holds.**
   - **Kept from the spec:** switching off refuses the capability's `start` commands and allows its `finish` commands.
     R4's alternative ("refuse switch-off while balances are open") is **not** adopted.
   - **Adopted from R4:**
     - the book guard never checks capabilities; core does;
     - `ref.business_type` drops `item_kinds`, `has_variants` and `has_calendar`;
     - a new `ref.capability_item_kind (capability, item_kind)` allows item kinds: counter→good, stock→good,
       bookings→service, stitching→service, orders→good, packages→package;
     - a new capability **`variants`** (requires `stock`; in the boutique pack) allows variant attributes;
     - `ops.site.booking_mode` requires `bookings`.
3. **Orders: the approved spec §3 holds, with R4 §6a's attach points:**
   - `books.order_line`: `price_id` or `quote_input_id → ops.member_input`, enforced with
     `check (num_nonnulls(price_id, quote_input_id) = 1)`. A stitching quote is the person's typed figure, labelled as
     theirs.
   - `books.sale_line` gains `order_line_id`, with `check (num_nonnulls(price_id, order_line_id) >= 1)`.
   - `books.outbound_message` gains `order_id`.
   - The taint allow-list (BLUEPRINT §7.8) gains `order.confirm`.
   - A contact's erasure is held while an open order or an unapplied advance exists.
   - A new watcher, **`advance_unapplied`**: an advance on a cancelled or delivered order that is neither refunded nor
     applied. Its impact is the advance, and there are 17 watchers in all.
   - **`ops.order_state`**: a derived row per order (current step, `step_no`, `due_on`, `trial_on`, `updated_at`),
     written by `z_order_state`, an AFTER INSERT trigger on `books.order_step` (the pattern of
     `z_outbound_delivery`). It has no direct write grant and the index `(tenant_id, step, due_on)`, and it serves the
     order board.
   - `21_orders.sql` adds the foreign keys from earlier files by `alter table`, so the build order never breaks (R4 B1's
     pattern):
     - `books.sale.order_id`;
     - `books.sale_line.order_line_id`;
     - `books.payment.order_id`;
     - `books.outbound_message.order_id`.
4. **Cache: the spec §5, narrowed by R4 §6c.**
   - **Cached:**
     - a release's pinned snapshots by release id;
     - pinned snapshots by id;
     - the slug → tenant, latest release and verified lookup, with a short TTL, invalidation on publish and verify,
       and negative entries that answer the same byte-identical 404.
   - **Computed per request, over the cached release (never cached):**
     - live overlays: `held` flags, offers in effect, slots.
   - **Always stays in Postgres:**
     - idempotency, `allow()`, sessions, hold caps, balances.
   - **Never in the cache:**
     - a screen read's result;
     - a name or a phone number.
5. **PostgreSQL 17 has no built-in `uuidv7()` (FACT: added in 18).**
   - `02_shared.sql` defines `ops.uuidv7()` in plpgsql (no row-type parameter, so B1 allows it there).
   - Every id defaults to it, so the tie-break `order by effective_from desc, created_at desc, id desc` (R4 K1) holds.
6. **BLUEPRINT §10 is replaced** by a pointer to `docs/superpowers/plans/2026-10-29-munshi-build-waves.md`.
7. **`docs/blueprint.html` is rebuilt after W1** (the founder is remote). Not in W0.
