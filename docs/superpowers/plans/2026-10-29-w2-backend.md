# W2 · Backend on the new schema: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move all of Munshi's backend (`packages/core`, the web app's server code, the seed) from the v1 database
(`db/migrations`) to the v2 schema files (`db/schema/00–90`). Build the W2 features on v2. Then delete v1. Every test
must be able to fail at every commit.

**Architecture:**
- **Three phases, then the flip.**
  - **W2a** runs now, beside the migrator. It contains only new code that needs nothing but files `00–09`.
  - **W2b, the spine,** moves today's code and its tests to v2 in **one integration commit**.
  - **W2c** builds the features in parallel lanes on the green v2 base.
  - **BP-FLIP** deletes v1.
  - Review R-A comes last.
- **Every lane works in its own git worktree.** A red-proof run edits source files and runs every suite, so two lanes
  in one tree would red-proof each other's half-written work. `main` stays the migrator's.

**Tech Stack:** TypeScript on Node 22 (`node file.ts`), pnpm 11, node-postgres 8.23.1, zod, and vitest. Tests run on
PostgreSQL 17 embedded through `db/test/v2/global-setup.ts` (config `db/vitest.v2.config.ts`).

**The spec is `docs/BLUEPRINT.md`** (§2.10 tables, §2.13 and §9 gates, §4 core, §6 sign-in, §7 AI, §8 features). Its
companions are the waves index (`2026-10-29-munshi-build-waves.md`, the W2 table) and the appendix
(`2026-10-29-appendix-bp-tickets.md`, the rows each ticket cites).
- Where this plan regroups a ticket, **this plan wins**.
- Where a table, gate or rule differs, **BLUEPRINT wins**.

## Why W2 changed shape (read this first)

**The waves index assumed each area could move to v2 while the v1 suites stayed green. That is false.** A read-only
mapping of the code (29 Oct) found:

| Fact | Where |
|---|---|
| Every command and read goes through one path: `withTx`, then `execute` and `runCommand`, then `journal()`, then `mintSnapshot` and `resolveRef` | `packages/core/src/{session,commands,snapshots,read}.ts` |
| Every core test builds its shop with `createTenant`, `addMember` and `runCommand` (`db/test/shop.ts`) or the kirana seed (`db/seed/kirana.ts`, which imports core) | 14 `db/test` files, `ms13-seed-stock`, 19 web files through `apps/web/test/home-db.ts` |
| v2 reshapes the tables that path writes | — |
| `snap.snapshot_cell` is gone; cells live in `snap.snapshot.rows` as jsonb | BLUEPRINT ≈ L1756 |
| `ops.run` and `ops.finding` become `ai.run` and `ai.finding` | — |
| Names and phones move to `ops.contact` | — |
| An item's name moves to `books.item_revision` | — |
| `journal_entry.memo` becomes `memo_code` | — |
| A payment's sign changes | — |
| 8 web server files (`apps/web/lib/server/{agent-port,hero,ledger,ops,bills,counter,credit,suppliers}.ts`) run their own SQL against v1 shapes; no W2 ticket owned them | — |

**So retargeting any of the shared path breaks every test that uses it, about 230 tests in 37 files.**
- That count is INFERENCE: it comes from a grep that does not expand `.each`. SPINE-0 measures the real number.
- About 95 v1 tests run raw SQL with no core: `g1`–`g12`, `people`, `sign-in`, `tenancy` and `ms13-*`. They stay on
  v1 until BP-FLIP.

**Rejected: taking those tests out of `pnpm check` while their code is rewritten.** Gates that cannot fail while
their code changes, and an unchecked kirana answer key, break the plan's own rules.

**Ruling:** today's code and its tests move to v2 **in the same commit** (the spine). The spine's three lanes work in
disjoint files of one worktree, and the orchestrator lands them as one commit. A run of commits where HEAD does not
build is Munim's gotcha 40.

## Ground rules for every W2 lane

- **Worktrees.**
  - The orchestrator creates each lane's worktree: `git worktree add ../munshi-wt/<ticket> -b w2/<ticket> main`.
  - It then runs `pnpm install --frozen-lockfile --offline` inside it.
  - Lanes never run git or pnpm. They use `node_modules/.bin/*` and `node <file>.ts`.
  - After each `BP-DB-n` commit on `main`, the orchestrator rebases each open lane branch onto `main`. This is
    conflict-free except index files, because no lane touches `db/schema`.
  - The orchestrator commits on the branch by ticket, rebases it, fast-forwards `main`, runs the full check on `main`
    and removes the worktree (disk: Munim's gotcha 37).
- **Where v2 tests live.**
  - Core tests that need a database go in `db/test/v2/core/<area>/*.test.ts`. The v2 config already includes
    `test/v2/**`.
  - Their red-proofs go in `db/test/v2/sabotage/core-<area>.ts`, joined in `db/test/v2/sabotage/index.ts`. The
    migrator also edits that index on `main`, so expect a one-line conflict; the orchestrator resolves it.
  - Web tests stay in `apps/web/test/`.
- **Red-proofs.** A lane alone in its worktree runs `node test/redproof.ts --only=v2` from `db/`. The spine's three
  lanes share one worktree, so they **do not** red-proof. The orchestrator does it at integration, on a quiet tree.
- **Counts are measured, never grepped.**
  - Run each suite with `--reporter=json --outputFile=<scratch>/<suite>.json`.
  - Every commit message gives, per area, the v1 tests deleted and the v2 tests added.
- **Successors.**
  - `db/test/v2/successors.json` maps every v1 test (by suite, file and full title from the SPINE-0 baseline) that no
    longer runs to the v2 test that replaces it, or to `"retired": "<reason>"`.
  - `scripts/w2-successors.ts` reads the baseline and the current JSON results. It exits 1 if a baseline test neither
    still runs nor has an entry, or if an entry names a test that did not run.
  - Red-proof: delete one entry, and it fails.
- **Unchanged throughout:**
  - `db/seed/kirana.answers.json`, the kirana answer key, is read-only for every lane;
  - C5 stays "5 of 5 planted kinds (8 of 8 situations) and nothing else";
  - every model call is recorded (`MUNSHI_MODEL_MODE=recorded`);
  - never read `.env` or `.run/`.
- **Done when (every ticket):**
  - `pnpm check` is green on `main` after the merge;
  - `pnpm redproof` is green, with the ticket's new gates shown red, then green, in its report;
  - G8 still holds;
  - the successor script exits 0;
  - the report gives counts per suite and a guarantee scan with both clauses, stated even when clean.
- **At most six Munshi agents at once,** the migrator and reviews included.
